# ADR-003: ベクトル検索方式

- 状態: 提案
- タスク: T0-5
- 作成日: 2026-09-25
- 計測環境: Apple M5 / 16 GB / macOS 27.0.1 / arm64（2026-10-29 に再計測）

## 文脈

埋め込みベクトルをSQLiteと組み合わせて検索する方式を比較する。T0-3の採用決定を待たず、候補モデルの代表的な次元数（512、768、1152）をすべて計測する。比較対象はself full scanとsqlite-vecとし、sqlite-vecを実行できない環境では未計測として記録し、結果を推測で補完しない。

## 計測前に固定した評価基準

以下を計測前コミットで固定する。計測後に重み、足切り条件、データ生成方法を変更しない。変更する場合は別コミットで理由を記録し、変更後の条件で再計測する。

### 比較条件

- 次元数: 512、768、1152
- 件数: 10,000、50,000、100,000
- 表現: f32、f16
- クエリ: 各条件で固定seedから生成した同一クエリ集合
- 実行: cold相当の初回1回を除外し、warm-up後に複数回測定
- 更新: 初期投入、追加、更新、削除、再起動後の検索

### 重み

| 評価項目 | 重み |
|---|---:|
| 検索時間（p95） | 35 |
| f16の検索結果再現率（f32のTop-kとの一致） | 20 |
| メモリ・保存容量 | 15 |
| 初期投入・更新・削除のコスト | 10 |
| Windowsでの利用可能性 | 10 |
| 依存関係・実装複雑度・ライセンス | 10 |

### 足切り条件

- 50,000件で設計目標の検索応答200msを超えた結果は、目標未達として明示する
- f16のTop-10再現率が95%未満の場合、f16を無条件採用しない
- 検索結果の決定性を再起動後も維持できない方式は不採用
- 追加・更新・削除でインデックスを壊す方式は不採用
- Windowsでの配布またはfallback方針を説明できない方式は不採用
- MITと両立しないライセンスの依存は不採用

## 計画

`tools/t0-5/vector_benchmark.rs` は、決定性のあるベクトル生成、f32/f16表現、full scan、SQLite BLOB保存、任意のsqlite-vec拡張ロード、p50/p95、メモリ・保存容量、Top-k一致率を記録する。SQLite拡張が利用できない場合は、`sqlite-vec: unavailable` として実行環境を記録する。

## 結果

### 再計測（2026-10-29）

最初の計測には、計測ツールの誤りが2つあった（PR #11 の Copilot の指摘）。直したうえで、全18条件を計測し直した。下の表と提案は再計測の値に置き換えた。

- f32 から f16 への変換で、丸めの桁上がりを捨てていた。f16 の再現率は、量子化の誤差ではなく変換の誤りを測っていた
- sqlite-vec の全ケースを同じ Python プロセスで続けて実行していたため、最大 RSS に前のケースのメモリが残っていた。今回はケースごとに別プロセスで計測し、Rust 側と同じく入力ファイルの読み込みから測った

計測環境は Apple M5 / 16 GB / macOS 27.0.1 / arm64。固定 seed の20クエリ、ウォームアップ3回、Top-10。コマンドは `tools/t0-5/README.md` のとおりで、Python の依存は `uv run --no-project --with numpy==2.5.3 --with sqlite-vec==0.1.9` で用意した。

| 方式 | 次元 | 件数 | 精度 | p50 / p95 | 最大 RSS | Top-10再現率 |
|---|---:|---:|---|---:|---:|---:|
| self full scan | 512 | 50k | f32 | 11.57 / 11.70 ms | 216 MB | 1.000 |
| self full scan | 512 | 50k | f16 | 38.89 / 69.07 ms | 262 MB | 1.000 |
| sqlite-vec | 512 | 50k | f32 | 19.46 / 22.71 ms | 145 MB | 1.000 |
| sqlite-vec | 512 | 50k | f16展開f32 | 19.26 / 25.09 ms | 299 MB | 1.000 |
| self full scan | 768 | 50k | f32 | 27.05 / 30.29 ms | 318 MB | 1.000 |
| sqlite-vec | 768 | 50k | f32 | 30.16 / 36.59 ms | 197 MB | 1.000 |
| self full scan | 1152 | 50k | f32 | 29.41 / 32.20 ms | 472 MB | 1.000 |
| self full scan | 1152 | 50k | f16 | 74.04 / 79.03 ms | 469 MB | 0.995 |
| sqlite-vec | 1152 | 50k | f32 | 30.00 / 30.68 ms | 269 MB | 1.000 |
| self full scan | 768 | 100k | f32 | 74.28 / 94.89 ms | 625 MB | 1.000 |
| sqlite-vec | 768 | 100k | f32 | 42.20 / 43.09 ms | 352 MB | 1.000 |
| self full scan | 1152 | 100k | f32 | 55.02 / 56.11 ms | 937 MB | 1.000 |
| self full scan | 1152 | 100k | f16 | 143.56 / 143.93 ms | 940 MB | 1.000 |
| sqlite-vec | 1152 | 100k | f32 | 58.08 / 59.49 ms | 506 MB | 1.000 |
| sqlite-vec | 1152 | 100k | f16展開f32 | 59.40 / 61.04 ms | 1.191 GB | 0.995 |

- 全条件で p95 は 200 ms 未満だった。50,000件・512次元の self full scan は 11.70 ms
- f16 の Top-10再現率は全条件で 0.995 以上になり、足切り（95%）を満たした。最初の計測で 0.960 だったのは変換の誤りによる
- 最大 RSS は、sqlite-vec（f32）のほうが self full scan より小さかった。最初の計測で sqlite-vec が大きく見えたのは、前のケースのメモリが残っていたため
- f16 の self full scan は、要素ごとに f32 へ戻すため f32 の約2.5〜3倍遅い。保存容量は半分になる
- sqlite-vec の f16-native は、0.1.9 の `vec0` で未対応のままだった

## 提案

**仮決定（DeepSeek、2026-10-27）**: 自前の全件走査を MVP の方式とする。ADR の状態は提案のままとする。

提案（再計測後）: MVP の初期方式は、自前の全件走査（f32）とする。全条件で p95 が目標の 200 ms を大きく下回り、追加の依存がなく、Windows でも同じ実装で動くため。ただし、最初の提案の理由のうち「メモリを増やさない」は再計測で成り立たなくなった。メモリは sqlite-vec のほうが小さい。件数が10万件を超える場合や、メモリが問題になった場合は、sqlite-vec を再検討する。f16 は再現率の足切りを満たしたが、検索が遅くなるため、保存容量が問題になるまでは採らない。採用の決定は人間が行う。
