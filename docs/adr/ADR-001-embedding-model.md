# ADR-001: 埋め込みモデル

- 状態: 提案
- タスク: T0-3
- 作成日: 2026-09-25
- 計測環境: Apple M5 / 16 GB / macOS 26.6.2 / arm64（Codex実機確認済み）

## 文脈

1つの画像・テキスト埋め込みモデルを、自然言語検索、類似画像検索、ゼロショット自動タグ、カスタムタグ学習の4機能で共有する。候補はCLIP/SigLIP系から3つ以上を選び、ONNX RuntimeとCore ML実行プロバイダで比較する。

評価セットは `docs/eval/README.md` の形式に従うユーザー管理のローカルデータを使う。評価セットのパスが提供されるまで、検索品質・タグ品質の正式な計測は開始しない。

## 評価方式の変更理由

当初は全画像に検索・タグの正解ラベルを事前付与する計画だった。しかし、実装計画は「上位結果を目視評価」としており、全件ラベルは準備負荷が大きく、候補モデルが実際に返す境界事例を十分に含まない可能性がある。このため、候補ごとの上位結果を合併して匿名化し、ランダム順で採点するプーリング＋ブラインド採点へ変更する。

この変更後も、カスタムタグ3〜5個のtrain/testだけは事前ラベルを使う。評価方式の変更は計測開始前であり、結果を見た後の基準変更ではない。

## 計測前に固定した評価基準

このADRの基準を計測前コミットで固定する。計測結果を見て重み、足切り条件、クエリ、タグ、ラベルを変更しない。変更が必要な場合は別コミットで理由を記録し、変更後の条件で再計測する。

計測結果は、候補ごとに生の値を `tools/t0-3/raw-results.csv` へ保存する。点数化後の表だけを保存してはならない。重みや上限を変更した場合は、生データを変更せず、`tools/t0-3/scoring.template.json` を更新して再計算する。

### 重み

| 評価項目 | 重み |
|---|---:|
| 自然言語検索（nDCG@10） | 20 |
| 類似画像検索（Recall@10） | 15 |
| ゼロショットタグ（タグ別APの平均） | 15 |
| カスタムタグ（テスト分割のmacro F1） | 15 |
| ロード時間（p95） | 10 |
| 推論時間（p95） | 15 |
| モデル合計サイズ | 5 |
| ピークメモリ | 5 |

合計100点。Tokenizer一致、ライセンス、ONNX/Core ML EP可否は配点に含めず、足切り条件として扱う。

### 生データから点数への換算

各指標は、ライセンス足切りと仮上限を通過した候補集合に対して、候補間のmin-max正規化を行う。値は0〜100点に変換し、重みを掛ける。

高いほど良い指標は次式とする。

```text
normalized = 100 * (value - min(value)) / (max(value) - min(value))
```

低いほど良い指標（ロード時間、推論時間、モデルサイズ、メモリ）は次式とする。

```text
normalized = 100 * (max(value) - value) / (max(value) - min(value))
```

候補間の値が同じ場合は、その指標を全候補100点とする。最終点数は各 `normalized / 100 * weight` の合計とする。評価対象から除外された候補はmin-maxの範囲に含めない。再計算は `tools/t0-3/score_results.py` で行い、英語fallback値は入力に保持するが点数計算には使用しない。

### 計測前のライセンス足切り

次の確認が完了しない候補はモデルをダウンロード・計測せず、不採用理由だけを候補表へ記録する。

- モデルウェイトのライセンスとバージョン
- モデルコードのライセンス
- TokenizerファイルとTokenizerコードのライセンス
- ONNX変換・量子化・変換スクリプトのライセンス
- 商用利用、再配布、帰属表示、NOTICE要件
- 使用する取得元URL、リビジョン、SHA-256

「オープンウェイト」「モデルカードにライセンス表記あり」だけでは合格としない。各構成要素の確認URLまたはライセンスファイルを記録する。

### その他の足切り条件

- 画像・テキストのどちらか一方を提供できない候補は不採用
- ONNXへ再現可能に変換できない候補は不採用
- Core ML EPまたはCPU fallbackのどちらも動かせない候補は不採用
- Rust側Tokenizerの出力が参照実装のtoken IDと一致しない候補は不採用
- 画像・テキスト埋め込みのcosine similarityが固定サンプルで0.999未満の候補は不採用
- 実測値を取得できない候補を、他候補の値で代用しない

### 仮の上限

以下は仮置きであり、あとから設定ファイルを変更して再計算できるようにする。上限を超えた候補は点数を下げるのではなく、ハード失格として扱う。

- モデル合計サイズ: 600 MB
- 推論時間 p95: 200 ms/画像
- ピークメモリ: 1.5 GB

### 固定する計測条件

- ユーザー提供の実写画像を使用し、検索・ゼロショットタグ・類似検索の全件正解ラベルは事前作成しない
- 画像推論はbatch size 1、ウォームアップ後に複数回測定する
- ロード時間、1枚あたりのp50/p95、ピークメモリ、モデルサイズを記録する
- CPUとCore ML EPを同一前処理・同一入力で比較する
- 日本語クエリを主評価とし、`query_en` の英語fallbackは参考値として別集計し、主評価の点数には含めない
- ゼロショットタグは設計書8.3を想定した20〜30語の固定語彙を使い、タグ別Average Precision（AP）の平均を主指標にする
- カスタムタグは`train`で分類器を学習し、未使用の`test`でmacro F1を算出する
- 参照実装とRust/ONNX実装の画像・テキスト出力を固定サンプルで比較する

### プーリングとブラインド採点

- 自然言語検索: クエリごとに各候補の上位20件を合併し、候補名を伏せてランダム順で0/1/2採点する。未採点は0としてnDCG@10を算出する
- ゼロショットタグ: タグごとに各候補の上位20件を合併し、同じ方法で採点する。1または2を関連ありとしてAPを算出する
- 類似画像検索: 固定したクエリ画像15枚程度について各候補の上位10件を合併し、0/1/2採点する。pool内関連画像に対するRecall@10とnDCG@10を算出する
- 採点項目の約10%を別位置へ重複して出題し、同一点を付けた割合を自己一致率として記録する
- 候補差はクエリ・タグ・類似クエリ画像を単位に10,000回のブートストラップを行い、差の95%信頼区間を記録する。区間が0をまたぐ場合は有意差なしと明記する
- 採点HTMLは `eval-data/` にだけ生成し、外部通信・CDNを使わない。候補名とrun IDを画面、HTMLソース、出力ファイル名へ含めない

### 計測前に固定する入力

`queries.csv`、`tags.csv`、`similarity-queries.csv` を計測前にコミットし、結合定義SHA-256をこのADRへ記録する。写真本体はコミットせず、類似クエリ画像のIDと画像SHA-256だけを固定する。

- クエリ定義SHA-256: 未確定
- タグ語彙SHA-256: 未確定
- 類似クエリ定義SHA-256: 未確定
- 結合定義SHA-256: 未確定

## 候補

候補の初期候補は次の3つ以上とする。日本語・多言語候補を含める。ライセンス欄は計測前に個別確認して埋め、未確認のまま計測しない。確認できない候補は `tools/t0-3/candidates.csv` に除外理由を記録する。

| 候補ID | モデルID | 公式参照先 | ライセンス状態 |
|---|---|---|---|
| siglip-base | `google/siglip-base-patch16-224` | Hugging Faceのモデルカード | ライセンス・実行経路確認済み、品質評価待ち |
| siglip2-base | `google/siglip2-base-patch16-224` | Hugging Faceのモデルカード | ライセンス・実行経路確認済み、サイズ上限超過 |
| siglip-multilingual | `google/siglip-base-patch16-256-multilingual` | Hugging Faceのモデルカード | ライセンス・実行経路確認済み、サイズ上限超過 |
| clip-japanese | `line-corporation/clip-japanese-base` | Hugging Faceのモデルカード | ライセンス・実行経路確認済み、品質評価待ち |
| rinna-japanese | `rinna/japanese-clip-vit-b-16` | Hugging Faceのモデルカード | 専用実行ソースを固定できず除外 |
| clip-base | `openai/clip-vit-base-patch32` | Hugging FaceのモデルカードとOpenAIの公式実装 | 配布ライセンス未確認のため除外 |

候補の追加・除外は `tools/t0-3/candidates.csv` に記録する。候補を除外した場合でも、除外理由と確認URLを残す。

### 今回のライセンス確認結果

- GoogleのSigLIP、SigLIP2、多言語SigLIPは、モデル、Transformers、Tokenizers/SentencePiece、Optimum/ONNX、ONNX Runtimeについて配布・実行経路のライセンスを確認し、リビジョン、ウェイトSHA-256、確認URLを候補表へ固定した。
- `line-corporation/clip-japanese-base` は再確認の結果、リポジトリ全体のApache-2.0 LICENSEがカスタムコードと提供ONNXを覆い、Tokenizer実装はApache-2.0、その依存元 `rinna/japanese-roberta-base` はMITと確認できたため候補へ戻した。
- `rinna/japanese-clip-vit-b-16` はモデルカードのApache-2.0とTokenizer依存元のMITまでは確認できた。しかし、モデルカードが参照する専用 `japanese-clip` ソースが取得不能で、モデルリポジトリにもTokenizer実装がないため、再現可能で保守可能な実行経路を固定できず除外した。
- `openai/clip-vit-base-patch32` は、今回確認したモデルページからモデルウェイトの商用再配布条件を確定できなかったため計測前に除外する。

詳細なURL、固定リビジョン、SHA-256、除外理由は `tools/t0-3/candidates.csv` を正とする。

## 結果

Core ML EPのセッションにはCPU EPもfallbackとして登録され、一部ノードだけがCore MLへ分割された。したがって、この表は「Core MLのみ」の速度ではない。今回のモデルではCPU単独の方が速く、Core ML利用を性能上の優位とは扱わない。`siglip-base` と `clip-japanese` のfp32画像経路はCore ML実行時に失敗したが、配布候補のf16経路はCPU/Core MLの双方でcosine 0.999以上を満たした。

検索nDCG@10、類似Recall@10、zero-shot mean AP、custom macro F1、英語fallback、自己一致率、ブートストラップ95%信頼区間は未計測である。ユーザーが入力を固定するまでランキングを生成していない。

## 提案

仮上限による足切りでは `siglip-base` と `clip-japanese` を品質評価対象として残す。ただし、これは採用提案ではなく、品質比較へ進める候補の絞り込みである。ユーザーが評価入力を固定し、ブラインド採点結果を人間がレビューするまで採用候補は記入しない。採用の決定はCodexが行わない。
