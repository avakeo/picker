# ローカル画像管理アプリ（仮称） 設計書

- バージョン: 0.1（ドラフト）
- 作成日: 2026-09-24
- ライセンス: MIT
- 対象読者: 実装担当（Codex）および作者

本書は決定事項と未決事項を区別して記述する。未決事項は実装計画のフェーズ0（技術検証）で決定し、`docs/adr/` に設計判断記録（ADR）として残す。実装中に本書と矛盾する必要が生じた場合は、実装を進めずに ADR の提案として記述すること。

## 1. 概要

Eagle のように、ユーザーの任意のフォルダにある画像を閲覧・タグ付け・検索できるデスクトップアプリ。以下の特徴を持つ。

- **参照型**: 画像は元の場所に置いたまま、アプリは索引とメタデータだけを持つ。原本ファイルは一切変更しない。
- **ローカルAIによる自動タグ付け**: 画像-テキスト埋め込みモデルをオンデバイスで実行し、自動タグ、類似画像検索、自然言語検索を提供する。
- **ユーザーフィードバックで賢くなるカスタムタグ**: ユーザーが数枚にタグを付けると残りの候補を提案し、承認・却下の結果から学習する。
- **完全ローカル**: ネットワーク通信はモデルファイルのダウンロードのみ。テレメトリなし。
- **配布**: GitHub でソース公開（MIT）、ビルド済みアプリは GitHub Releases で配布（Developer ID 署名＋公証）。

## 2. 目標と非目標

### 2.1 MVP の目標

- macOS（Apple Silicon）で動作する。
- 任意フォルダを登録し、実写写真を閲覧・手動タグ付け・検索できる。
- 自動タグ（ゼロショット）、類似画像検索、自然言語による意味検索ができる。
- カスタムタグの少数例提案と、承認・却下によるフィードバック学習ができる。
- 完全一致・近似の重複画像を検出できる。
- ユーザーの判断データ（確定・却下したタグ等）をポータブルな形式で書き出せる。

### 2.2 MVP の非目標（将来フェーズで対応）

- Windows 対応（設計上は常に考慮する。第7章参照）
- iOS / Android 対応
- 2次元イラスト対応（Danbooru 系タガー、レーティング判定）
- OCR
- Laya による判断（スマートフォルダ振り分け等）
- RAW 画像、動画
- クラウド同期、複数端末共有
- Mac App Store 配布

## 3. 設計原則

1. **ファイルが真実の源である。** アプリの DB は消しても作り直せる索引であり、原本ファイルは読み取り専用として扱う。
2. **再生成できるデータと、できないデータを分ける。** サムネイル・埋め込み・自動タグ候補・EXIF キャッシュは再計算できる。ユーザーが確定・却下したタグ、カスタムタグ定義、タグの階層やエイリアスは人間の判断であり再生成できない。後者だけは確実に保全し、書き出せるようにする。
3. **すべてのモデルは差し替え可能な境界の背後に置く。** 埋め込み・タグ付け・判断の各モデルは共通の入出力境界を通して呼び出し、モデルの交換や追加が境界の実装追加だけで済むようにする。
4. **ローカル完結。** 推論はすべてオンデバイス。外部APIへの接続は、境界上は可能でも既定では無効とする。
5. **依存は最小限。** 知覚ハッシュ、ベクトル近傍探索、線形分類器のような単純なアルゴリズムは自前実装を優先する。依存を追加する場合は目的・ライセンス・代替案を明記する。
6. **処理はいつ中断されても再開できる。** 各画像の処理段階を DB に記録し、アプリ終了や強制終了後も続きから再開する。
7. **OS 依存部分はトレイトの背後に隔離する。** 画像デコード、OCR、推論アクセラレータなど OS 固有の実装は抽象境界の裏に置き、Windows 対応時は実装の追加で済むようにする。
8. **UI は契約の利用者であり、差し替え可能である。** UI とコアの間のやり取りは `ui-contract.md` で定義した操作・通知・データ型に限る。UI は契約以外の手段でコアに触れず、ビジネスロジックを持たない。これにより、開発中の仮UIをデザイナーによる本番UIに置き換えても、コアには変更が生じない。

## 4. 決定事項一覧

| 項目 | 決定 | 理由 |
|---|---|---|
| 対象 OS | MVP は macOS（Apple Silicon）。次に Windows | Mac が主環境。Eagle 型のフォルダ管理はデスクトップ向き |
| アプリ基盤 | Tauri v2 | デスクトップで成熟、軽量、Rust コアと直結 |
| コア言語 | Rust（Cargo workspace で機能別クレートに分割） | 性能、安全性、Mac/Windows 共通化 |
| UI | Svelte 5 + TypeScript | 軽量で依存が少ない（最終確認はフェーズ0） |
| UI デザイン | デザイナーが Figma で作成。開発中は装飾なしの仮UIで機能を検証し、デザイン確定後に本番UIへ置き換える | UI とコアを並行して進めるため |
| UI とコアの境界 | `ui-contract.md` で定義。データ型は Rust 側を正とし、TypeScript の型は自動生成する | 型の二重管理と食い違いを防ぐ |
| 推論ランタイム | ONNX Runtime（macOS は Core ML 実行プロバイダ、Windows は DirectML 実行プロバイダ） | OS 横断で同じモデル形式を使える |
| DB | SQLite（WAL モード） | 組み込み可能、全 OS で安定 |
| ベクトル検索 | MVP は自前の全件走査。sqlite-vec はフェーズ0で評価 | 想定規模では全件走査で十分速く、依存が減る |
| 画像の識別子 | ファイル内容の BLAKE3 ハッシュ | 移動・改名に強い。パス表記の OS 差に影響されない |
| 管理方式 | 参照型（取り込み・コピーしない） | 原則1 |
| 確定タグの永続化 | SQLite ＋ JSON エクスポート ＋ XMP サイドカー（任意） | 原則2 |
| 配布 | GitHub Releases、Developer ID 署名＋公証 | 外部配布。サンドボックス制約を避ける |
| ライセンス | MIT | ポートフォリオとして見てもらいやすい |

## 5. アーキテクチャ

### 5.1 層構成

上から順に、UI 層、アプリ層、コア層、プラットフォーム層の4層とする。

- **UI 層（Svelte）**: 仮想グリッド、詳細パネル、フォルダツリー、タグ管理、レビュー画面、設定画面。表示とユーザー操作のみを担い、ビジネスロジックを持たない。
- **アプリ層（Tauri）**: UI からのコマンド受付、進捗などのイベント通知、サムネイル配信用のカスタムプロトコル。
- **コア層（Rust クレート群）**: ドメインモデル、インデックス処理、ML 推論境界、学習、永続化。
- **プラットフォーム層**: OS 固有の画像デコーダ、推論アクセラレータ、ファイル監視、（将来）OCR。

### 5.2 クレート構成

| クレート | 責務 |
|---|---|
| `app`（src-tauri） | Tauri コマンド、イベント、カスタムプロトコル、起動処理 |
| `core` | ドメインモデル（アセット、タグ、割当など）、ユースケース |
| `store` | SQLite アクセス、マイグレーション、リポジトリ |
| `indexer` | ジョブキュー、処理段階の実行と再開 |
| `fswatch` | フォルダ監視、起動時差分スキャン、ボリュームのオンライン判定 |
| `imaging` | デコード（プラットフォーム境界）、向き補正、サムネイル、EXIF、知覚ハッシュ |
| `ml` | 推論境界（Embedder / Tagger / Decider）、ONNX 実装、モデルレジストリ |
| `learn` | カスタムタグ分類器、候補スコアリング、レビュー候補の選定 |
| `sidecar` | XMP の読み書きとマージ、JSON エクスポート・インポート |

依存方向は `app` → `core` → 各機能クレートとし、機能クレート同士の循環依存を禁止する。OS 固有コードは条件付きコンパイルで隔離し、必ずトレイトの背後に置く。

### 5.3 データの流れ

1. ユーザーがフォルダ（ルート）を登録する。
2. スキャナが画像ファイルを列挙し、ファイル位置を記録してジョブを投入する。
3. インデクサが段階ごとに処理する（ハッシュ → メタデータ → サムネイル → 知覚ハッシュ → 埋め込み → 自動タグ → カスタムタグ候補）。
4. UI はサムネイルをカスタムプロトコル経由でアセット ID 指定で取得し、仮想グリッドに表示する。
5. ユーザーのタグ付け・承認・却下はフィードバックイベントとして記録され、カスタムタグ分類器の再学習と候補の再計算を起動する。
6. ファイル監視が変更を検知すると、該当ファイルのみ再処理する。

### 5.4 UI とコアの契約

UI とアプリ層の間は、次の3種類の経路だけでつながる。詳細は `ui-contract.md` に定義する。

- **コマンド**: UI からコアへの要求と応答（一覧取得、タグ付与、検索など）。
- **イベント**: コアから UI への通知（インデックス進捗、サムネイル生成完了、タグ変更など）。
- **サムネイル配信**: カスタムプロトコルによる画像データの取得（アセット ID とサイズのみ指定）。

契約の変更は仕様書の更新を伴うこととし、互換性を壊す変更は ADR に記録する。コマンドとイベントについては契約テスト（仕様どおりの型と挙動であることの検証）を用意し、UI を差し替えても契約が守られていることを確認できるようにする。

### 5.5 仮UI と本番UI

- **仮UI**: M1〜M3 の期間、コアの機能を確認するために作る装飾なしの UI。見た目の作り込みは行わない。
- **本番UI**: デザイナーが Figma で作成したデザインを実装したもの。色・余白・文字サイズなどはデザイントークンとして CSS 変数に落とし込む。
- 本番UIの実装完了時に仮UIのコードは削除する。
- デザイナーへの依頼内容は `design-brief.md` にまとめる。

## 6. データモデル

SQL は実装側で定義する。ここでは各エンティティの意味と主要な属性を示す。

### 6.1 エンティティ

| エンティティ | 意味 | 主要な属性 |
|---|---|---|
| Root | 登録された監視フォルダ | ID、絶対パス、ボリューム識別子、表示名、有効/無効、状態（オンライン/オフライン） |
| Asset | 画像の実体（内容で同定） | ID、BLAKE3 ハッシュ、ファイルサイズ、幅・高さ、形式、撮影日時、知覚ハッシュ |
| Location | Asset がディスク上のどこにあるか | ID、Asset ID、Root ID、Root からの相対パス、更新日時、状態（存在/欠落/オフライン） |
| Tag | タグの定義 | ID、名前空間、正規名、日本語表示名、英語表示名、親タグ ID、色、作成元 |
| TagAlias | タグの別名・表記ゆれ | タグ ID、別名 |
| TagAssignment | 画像へのタグ付与 | Asset ID、タグ ID、状態、出どころ、確信度、モデル ID とバージョン、更新日時 |
| CustomTagModel | カスタムタグの学習状態 | タグ ID、方式（プロトタイプ/ロジスティック回帰）、パラメータ、学習日時、学習に使った正例・負例数 |
| Embedding | 画像の埋め込みベクトル | Asset ID、モデル ID とバージョン、次元数、ベクトル（BLOB） |
| StageState | 各画像の処理段階の状態 | Asset ID（または Location ID）、段階名、状態、アルゴリズム/モデルのバージョン、エラー内容 |
| Job | 処理待ちの作業 | ID、対象、段階、優先度、試行回数、状態 |
| FeedbackEvent | ユーザーの判断履歴 | Asset ID、タグ ID、操作（承認/却下/手動付与/手動削除/取り消し）、提示時の確信度、日時 |
| Model | 導入済みモデル | ID、種別、バージョン、ファイルパス、SHA-256、ライセンス |
| Setting | 設定値 | キー、値 |

1つの Asset は複数の Location を持てる（同一内容のファイルが複数箇所にある場合）。タグは Asset に付くため、完全一致の重複ファイルは自動的に同じタグを共有する。

### 6.2 タグ割当の状態と出どころ

**状態**は次の3つ。

- `suggested`: システムが提案した未確認のタグ
- `confirmed`: ユーザーが付与または承認したタグ
- `rejected`: ユーザーが却下したタグ

**出どころ**は MVP では次の3つ。将来フェーズで追加される。

- `zero_shot`: ゼロショット自動タグ
- `custom_classifier`: カスタムタグ分類器の提案
- `user`: ユーザーの手動付与

将来追加予定: `vision`（Apple Vision 等の OS 標準分類）、`danbooru`（イラスト用タガー）、`rating`（レーティング判定）、`laya`（判断モデル）。

**不変条件**

- `confirmed` と `rejected` は自動処理によって上書きされない。変更できるのはユーザー操作のみ。
- `rejected` になった組み合わせ（画像とタグ）は、モデルを再実行しても再提案しない。
- 自動処理が書き込めるのは `suggested` のみ。再計算時は同じ出どころの `suggested` だけを置き換える。

### 6.3 データの分類

| 分類 | 対象 | 扱い |
|---|---|---|
| 再生成可能 | サムネイル、埋め込み、`suggested` の割当、EXIF キャッシュ、知覚ハッシュ、StageState、Job | 消えても再計算できる。バックアップ不要 |
| 再生成不可能 | `confirmed` / `rejected` の割当、手動作成したタグ・エイリアス・階層、カスタムタグ定義、FeedbackEvent、Root 設定 | エクスポート対象。DB スナップショットで保全 |

## 7. 取り込みとインデックス

### 7.1 ルート登録

ユーザーはフォルダを選んでルートとして登録する。ルートの下は再帰的に走査する。シンボリックリンクは辿らない（ループと想定外の範囲の走査を防ぐため）。隠しファイルと隠しフォルダは除外する。

### 7.2 同一性の判定

1. ファイルサイズと更新日時が前回と同じなら、内容は変わっていないとみなす（ハッシュ計算を省略）。
2. 変わっていれば BLAKE3 ハッシュを計算する。
3. 既存の Asset と同じハッシュなら、その Asset に Location を紐付ける。これにより移動・改名されたファイルのタグが引き継がれる。
4. 元の Location が見つからなくなった場合は、すぐに削除せず「欠落」とし、一定期間後または次回のフルスキャンで確定する。

### 7.3 フォルダ監視と差分スキャン

- OS のファイル変更通知を用いて監視する（macOS は FSEvents、Windows は変更通知 API。Rust の監視ライブラリで共通化）。
- 通知は短時間に集中するため、一定時間まとめてから処理する（デバウンス）。
- 通知は取りこぼしがあり得るため、起動時とルートのオンライン復帰時に差分スキャンを行う。
- 外付けドライブや NAS が外れている場合、そのルート配下は削除扱いにせず「オフライン」とする。オフラインの画像もキャッシュ済みサムネイルとタグで閲覧・検索できる。

### 7.4 処理段階

| 段階 | 入力 | 出力 | 再生成 |
|---|---|---|---|
| hash | ファイル | BLAKE3、サイズ | 可 |
| metadata | ファイル | 寸法、形式、EXIF（撮影日時、機種、GPS の有無） | 可 |
| thumbnail | ファイル | 2サイズのサムネイル（グリッド用と詳細用） | 可 |
| phash | サムネイル | 知覚ハッシュ（dHash） | 可 |
| embedding | 画像 | 埋め込みベクトル | 可 |
| auto_tag | 埋め込み | `zero_shot` の `suggested` 割当 | 可 |
| custom_suggest | 埋め込み | `custom_classifier` の `suggested` 割当 | 可 |

各段階は使ったアルゴリズムまたはモデルのバージョンを記録する。バージョンが上がった場合は、その段階と下流の段階だけを再処理対象にする。

### 7.5 ジョブキュー

- SQLite 上に永続化し、アプリの終了・強制終了後も続きから再開できる。
- 優先度を持つ。**UI で現在表示されている画像を最優先**で処理し、ユーザーが見ている範囲からサムネイルやタグが揃うようにする。
- 段階ごとに並列度を設定できる（デコードは CPU、推論はアクセラレータなど、ボトルネックが異なるため）。
- 失敗したジョブは回数上限つきで再試行し、上限を超えたらエラーとして記録して UI に表示する。
- 一時停止・再開ができる。バッテリー駆動時に自動で並列度を下げる設定を持つ。

### 7.6 対応形式とデコード

- MVP の対応形式: JPEG、PNG、HEIC/HEIF、WebP。
- デコードはプラットフォーム境界の背後に置く。macOS では OS 標準の画像処理基盤（ImageIO）を使い、HEIC を含めて扱う。JPEG・PNG・WebP には Rust 実装のフォールバックを持つ。
- EXIF の向き情報を反映し、色空間は sRGB に揃える。

### 7.7 入力の安全性

- ファイルサイズと画素数に上限を設け、超えるものは処理せず記録する（解凍爆弾対策）。
- デコードは専用のワーカーで行い、失敗やパニックがアプリ全体に波及しないようにする。
- 1枚あたりの処理時間に上限を設ける。
- 将来的にはデコードを別プロセスに分離することを検討する。

## 8. 画像理解（ML パイプライン）

### 8.1 推論境界

すべてのモデルは次の3種類の境界のいずれかを通して呼び出す。どの実装も、結果とともにモデル ID とバージョンを返す。

- **Embedder**: 画像を埋め込みベクトルに変換する。テキストを同じ空間のベクトルに変換する。次元数を公開する。
- **Tagger**: 画像（または埋め込み）から、タグと確信度の一覧を返す。
- **Decider**: Jev 互換の入出力を持つ判断境界。状態（テキストや構造化データ）と型付きの質問を受け取り、確率付きの回答を返す。質問の型は次の3つに限定する。
  - `choice`: 選択肢の中からの確率分布
  - `score`: 順序付きルーブリックの期待値
  - `noul`: 命題が真である確率

モデルの導入・更新は**モデルレジストリ**が管理する（第8.6節）。

### 8.2 MVP の実装方針：1つの埋め込みモデルで4機能

MVP では画像-テキスト埋め込みモデル（CLIP / SigLIP 系）を1つだけ導入し、次の4機能をまかなう。

1. 類似画像検索（画像埋め込み同士の近さ）
2. 自然言語による意味検索（テキスト埋め込みと画像埋め込みの近さ）
3. ゼロショット自動タグ（タグ語彙のテキスト埋め込みとの近さ）
4. カスタムタグの学習と提案（第8.4節）

これにより、MVP の時点から OS 非依存でモデルは1つで済む。Apple Vision の標準画像分類は、将来の追加 Tagger 実装（macOS 限定）として扱う。

**モデル選定基準**（フェーズ0で評価し ADR に記録）

- 再配布・商用利用が可能なライセンスであること
- ONNX 形式で入手またはエクスポートできること
- Core ML 実行プロバイダで動作すること
- モデルサイズと推論速度（1枚あたりの時間、ロード時間、メモリ）
- 日本語クエリでの検索品質。英語専用モデルの場合は、タグ名の日英辞書による変換などの代替策を用意する

### 8.3 ゼロショット自動タグ

- **タグ語彙ファイル**をリポジトリに同梱する。各エントリは、タグ ID、英語プロンプト、日本語表示名、英語表示名、カテゴリ、タグ別閾値を持つ。初版は実写向けに数百語程度から始める。
- 英語プロンプトはテンプレート（「〜の写真」に相当する文型）で複数作り、テキスト埋め込みを平均して使う。
- 画像埋め込みとタグ埋め込みの類似度を確率に変換し、閾値を超えたものを `suggested` として登録する。
- 閾値はタグ別に調整できるようにし、評価用の小さなラベル付き画像セットで精度を測って決める。
- 語彙の埋め込みは起動時に一度だけ計算してキャッシュする。

### 8.4 カスタムタグの学習

ユーザーが自由に定義するタグ。既存の語彙にない概念（「自作ロボットの写真」など）を扱う。

**段階A：プロトタイプ方式（正例が3枚以上）**

正例画像の埋め込みの平均（プロトタイプ）を作り、全画像との類似度で候補をスコアリングする。

**段階B：ロジスティック回帰（正例・負例が一定数以上、目安は各10件）**

タグごとに、埋め込みを入力とする L2 正則化付きロジスティック回帰を学習する。実装は自前で行う。負例は、ユーザーが却下した画像を優先し、不足分は他のタグで確定済みの画像から抽出する。

**再学習**

フィードバックが一定件数溜まるたび、またはレビュー画面を閉じたときに再学習する。学習と全件スコアリングは、目安として数万枚規模で1秒以内に終わることを目標とする。

**タグ名からの初期提案**

正例がまだない段階でも、タグ名や説明文のテキスト埋め込みを使ったゼロショットで初期候補を出せるようにする。

### 8.5 能動学習とレビュー

ユーザーに正誤を尋ねる対象を賢く選び、少ない操作で精度を上げる。

- **候補の選び方**: 確率が判定境界付近の画像（モデルが迷っているもの）を優先する。ただし境界付近だけだと不正解が多くユーザーが疲れるため、高スコアの候補も一定割合混ぜる。
- **レビュー UI**: 「このタグの候補」を20枚程度のグリッドで提示し、ユーザーは違うものだけを外す。確定操作で、残したものは承認、外したものは却下として記録する。キーボード操作と取り消しに対応する。
- 自動タグ（`zero_shot`）にも同じレビュー UI を使えるようにする。

### 8.6 モデルレジストリ

- モデルファイルはアプリ本体に同梱せず、初回起動時または機能の有効化時にダウンロードする。
- ダウンロード元 URL と SHA-256 ハッシュはアプリ内に固定する。ハッシュが一致しないファイルは読み込まない。
- 通信は HTTPS のみ。
- モデルごとにライセンス情報を保持し、アプリ内の「このアプリについて」画面で表示する。
- 複数バージョンを保持でき、切り替えた場合は該当する処理段階が再処理対象になる。

### 8.7 将来フェーズの拡張（参考）

- **Decider（Laya）**: ローカルの Laya（ONNX）を Decider 境界の実装として追加し、タグ・EXIF・OCR テキストから組み立てた状態記述をもとに、スマートフォルダ振り分け（choice）、保存優先度（score）、個人情報を含むか（noul）などを判定する。確率の較正（温度パラメータ）、`noul` のラベル上書き、位置バイアスなど、モデルごとの癖の補正設定を境界の実装側に持たせる。本家 Jev などの外部 API も境界上は接続可能だが、既定では無効とする。
- **OCR**: macOS は Vision、Windows は OS 標準 OCR をプラットフォーム境界の背後に実装する。OCR テキストは全文検索の対象にする。
- **イラスト対応**: 写真とイラストの判別を行い、イラストには Danbooru 系タガーを追加の Tagger として適用する。レーティング出力を使い、センシティブな画像のサムネイルを自動で伏せる機能を提供する。

## 9. 閲覧と検索

### 9.1 グリッド表示

- 仮想スクロールで、画面内と前後数行分のみ描画・保持する。
- レイアウト方式（縦横比を保つメイソンリーか、正方形に切り抜く均等グリッドか）はデザイナーと合意して決める（第15章）。メイソンリーの場合、各画像の縦横比はメタデータ段階で取得済みのため、サムネイル生成前でも配置を計算できる。
- サムネイルはアプリ層のカスタムプロトコルで配信する。リクエストはアセット ID とサイズのみを受け付け、ファイルパスは受け付けない。
- サムネイル未生成の画像はプレースホルダを表示し、生成され次第差し替える。表示中の画像は処理優先度を上げる（第7.5節）。

### 9.2 検索とフィルタ

- **タグフィルタ**: AND / OR / NOT の組み合わせ。状態（未確認のみ、確定のみ）でも絞り込める。
- **属性フィルタ**: ルート・フォルダ、撮影日時、形式、寸法、ファイルサイズ。
- **テキスト検索**: タグ名・エイリアスの一致と、埋め込みによる意味検索を組み合わせる。タグ名が一致した結果を上位に置き、その後に意味検索の結果を続ける。
- **類似画像検索**: 選択した画像の近傍を表示する。
- **重複検出**: 完全一致（同一ハッシュで Location が複数）と、近似（知覚ハッシュのハミング距離が閾値以下）を一覧表示する。

### 9.3 詳細パネル

- 大きめのプレビュー、EXIF 情報、ファイルの場所（Finder で表示）。
- 付与されたタグを、出どころ・状態・確信度が区別できる形で表示する。`suggested` はその場で承認・却下できる。
- GPS 情報は有無と座標の表示のみ行う。地図表示など外部通信を伴う機能は持たない。

## 10. タグ体系

### 10.1 名前空間

| 名前空間 | 内容 | フェーズ |
|---|---|---|
| `general` | 同梱語彙によるゼロショット自動タグ | MVP |
| `custom` | ユーザー定義の学習するタグ | MVP |
| `user` | ユーザーが手動で付ける通常のタグ | MVP |
| `vision` | OS 標準の画像分類 | 将来 |
| `danbooru` | イラスト用タガー | 将来 |

`custom` と `user` の違いは、学習による候補提案を行うかどうか。`user` タグは後から `custom` に切り替えられる。

### 10.2 表示名・エイリアス・階層

- タグは日本語と英語の表示名を持つ。UI は日本語を既定とする。
- エイリアスにより表記ゆれ（「ネコ」「猫」「cat」など）を同じタグに寄せる。
- タグは親子関係を持てる（Eagle のタググループに相当）。親タグでフィルタすると子タグも含める。

## 11. 永続化とポータビリティ

### 11.1 データベース

- アプリのデータディレクトリに SQLite ファイルを1つ置き、全ルートを管理する。
- WAL モードで動作させ、UI の読み取りとインデクサの書き込みを並行させる。
- スキーマ変更はバージョン付きマイグレーションで行い、既存のマイグレーションは書き換えない。
- パスはルート ID とルートからの相対パスで保持し、ルートフォルダ自体の移動にも対応できるようにする。
- 再生成不可能データの保全のため、定期的に DB のスナップショットを取る。

### 11.2 エクスポートとインポート

- 再生成不可能データ（第6.3節）を JSON で書き出す。画像はパスではなく BLAKE3 ハッシュで参照するため、別のマシンやフォルダ構成でもインポートできる。

### 11.3 XMP サイドカー（任意機能）

- 確定したタグのみを、画像の隣に XMP サイドカーとして書き出す。
- タグはキーワードの標準フィールドに、階層は階層キーワードのフィールドに書く。
- ファイル名は「元のファイル名（拡張子込み）＋ .xmp」とする。同名で拡張子違いのファイルの衝突を避けるためで、拡張子を除いた名前を使う一部ソフトとの互換性は下がる（ADR に記録）。
- 既存の XMP がある場合は、他ソフトが書いた項目を保持したままマージする。
- ユーザーのフォルダにファイルを作るため、既定は無効とし、設定で有効化する。

### 11.4 Finder タグ同期（将来）

確定タグを macOS の Finder タグと同期するオプション。Spotlight や Finder からも同じタグで検索できるようになる。

## 12. セキュリティとプライバシー

### 12.1 脅威と対策

| 脅威 | 対策 |
|---|---|
| 悪意のある画像ファイル（デコーダの脆弱性、解凍爆弾） | サイズ・画素数・処理時間の上限。OS 標準デコーダの利用。デコード失敗の隔離。将来はプロセス分離 |
| モデルファイルの改ざん・すり替え | アプリ内に固定した SHA-256 で検証し、不一致なら読み込まない。HTTPS のみ |
| Webview 経由の攻撃（ファイル名等に仕込まれたスクリプトから IPC を悪用） | Tauri の権限設定を最小化。厳格な CSP。ファイル名や EXIF など外部由来の文字列は必ずテキストとして描画し、HTML として解釈しない。リモートコンテンツを読み込まない |
| カスタムプロトコル経由のパストラバーサル | パスではなくアセット ID のみ受け付け、キャッシュディレクトリ外のファイルを返さない |
| SQL インジェクション | パラメータ化クエリのみを使う |
| XMP・EXIF の解析を狙った攻撃（XML 外部実体参照など） | XML パーサで外部実体と DTD を無効化。解析サイズの上限 |
| サプライチェーン攻撃 | 依存の最小化、ロックファイル、Rust 依存の脆弱性とライセンスの自動検査、JavaScript 依存の監査、SBOM の公開、署名・公証、リリース成果物のハッシュ公開 |
| プライバシー漏洩 | ネットワーク通信はモデルのダウンロードのみ（接続先を固定）。テレメトリなし。GPS 情報はローカル表示のみ |

### 12.2 前提と制限

- ローカル DB にはファイルパスとタグが含まれるが、MVP では DB を暗号化しない。OS のディスク暗号化に依存することをドキュメントに明記する。
- 脅威モデルの詳細は `docs/security/threat-model.md` に記述し、機能追加のたびに更新する。

## 13. 非機能要件（暫定目標）

以下は暫定値であり、フェーズ0の計測結果をもとに確定する。

| 項目 | 目標 |
|---|---|
| 起動時間 | 索引済み5万枚のライブラリで2秒以内に操作可能 |
| スクロール | グリッドのスクロールで 60fps を目標とし、UI スレッドをブロックしない |
| メモリ | アイドル時 300MB 以内（モデル読み込み時は別途計測して定める） |
| 初回インデックス | 1万枚あたりの所要時間をフェーズ0で計測し、目標を設定する |
| 検索応答 | タグフィルタ・意味検索とも、5万枚で 200ms 以内 |
| カスタムタグ再学習 | 数万枚規模で1秒以内 |

## 16. 用語集

| 用語 | 意味 |
|---|---|
| 参照型 | 画像をコピーせず、元の場所のまま索引だけを持つ管理方式 |
| ルート | ユーザーが登録した監視対象のフォルダ |
| アセット | 内容ハッシュで同定される画像の実体 |
| 埋め込み | 画像やテキストを意味的な近さが距離で表れるベクトルに変換したもの |
| ゼロショット | 学習なしで、タグ名などのテキストとの近さだけで分類すること |
| プロトタイプ | あるタグの正例画像の埋め込みの平均 |
| 能動学習 | モデルが迷っているデータを優先してユーザーに尋ね、少ない回答で精度を上げる手法 |
| 知覚ハッシュ | 見た目が似た画像ほど近い値になるハッシュ。重複・類似検出に使う |
| サイドカー | 画像の隣に置くメタデータファイル（XMP） |
| ADR | 設計判断記録。何をなぜ決めたかを残す文書 |
| Jev 互換 | choice / score / noul の3つの型付き質問に確率付きで答える入出力形式 |
